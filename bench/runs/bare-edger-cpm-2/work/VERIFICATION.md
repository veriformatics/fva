# Verification results

R1 has an intermediate-overflow counterexample to its unrestricted mathematical
CPM guarantee. R2 has a threshold counterexample with small integer counts,
even when the documented total-count requirement is satisfied. The original
software, documentation, and compiled artifact have not been changed.

The results combine executions of the exact shipped WebAssembly bytes and R
files with Lean proofs about the exact values in those executions. They are
counterexamples, not a proof of general correctness or a formalization of an
entire WebAssembly/R runtime.

## R1: intermediate overflow

Use a one-row, one-column matrix with count and library size both equal to
`0x1p+1023` (that is, `2^1023`). Both are finite, positive, exactly representable
binary64 values. The initial output buffer contains that count; `nthreads=1`.

* The exact mathematical result `c / L * 1000000` is **1000000**.
* Executing the original exported `calc_cpm_raw` returns **positive infinity**.
* The artifact multiplies the count by `1000000` before dividing by the library
  size. That intermediate product overflows. A separately executed binary64
  divide-first expression returns exactly **1000000** for the same inputs.

These are `assert_return` checks generated by
[verification/check.py](verification/check.py), using the caller in
[verification/probe.wat](verification/probe.wat). They execute the original
function, including its actual matrix indexing, allocation, and library-size
extraction. The overflow is not inferred solely from the C source.

There is **no finite absolute or relative error bound over the unrestricted
finite inputs in R1**: this input has finite exact output and infinite computed
output. This is avoidable intermediate overflow, rather than unavoidable
rounding of an unrepresentable final result. If “as double-precision arithmetic
allows” is intended to permit this intermediate overflow, the execution is
consistent with that weaker interpretation; no universal accuracy theorem for
that interpretation is claimed here. A useful finite error theorem needs
additional range assumptions, which README.md does not state.

For an ordinary finite input, the proved rounding error is also explicit:
for `c=10`, `L=18`, the artifact output minus the exact CPM is
`-1/19327352832`; its absolute relative error is
`1/10737418240000000`. This is a certificate for this input, not a general error
bound. The Lean statements below certify both the finite-input error and the
exact arithmetic behind the overflow witness.

## R2: a gene at min.count is discarded

Run the default matrix method with all tuning parameters at their defaults:

```r
y <- matrix(c(10,8,10,8), nrow=2, ncol=2)
lib.size <- c(18,18)  # also exactly colSums(y)
filterByExpr(y, lib.size=lib.size)
```

The columns are `(10,8)` and `(10,8)`. No group or design is supplied, so the
required sample size is 2. The median library size is 18. The first gene has
count 10 in both samples and total count 20, exceeding `min.total.count=15`.
Thus it meets the documented minimum-count rule, including the documented
median-library scaling and the additional total-count condition.

The actual values for the first gene are:

| Value | Exact binary64 encoding | Decimal rendering |
| --- | --- | --- |
| Artifact CPM in each sample | `0x4120f4471c71c71c` | `555555.5555555555` |
| R cutoff `10 / median(lib.size) * 1e6` | `0x4120f4471c71c71d` | `555555.55555555562` |

They differ by exactly one ULP, `2^-33`. The kernel computes
`(count * 1e6) / L`, while the cutoff computes `(min.count / median(L)) * 1e6`.
Their distinct rounding paths make **zero** samples pass the CPM comparison.
The R tolerance is applied to the number of passing samples, not the CPM
cutoff, and cannot rescue this case.

The documented count-based result is `c(TRUE,FALSE)`; the checked execution
returns **`c(FALSE,FALSE)`**. Lowering `min.count` to 9 returns `c(TRUE,FALSE)`;
lowering it to 8 returns `c(TRUE,TRUE)`. These controls use the same actual
artifact output. This failure does not rely on omitting the documentation's
extra total-count test.

This interprets R2 as the stated count threshold with mathematical CPM scaling.
If the documentation's `CPM >= CPM.cutoff` formula is instead defined to mean
comparison of these separately rounded values, the implementation follows
that formula on this input, but it does not implement the exact count-threshold
interpretation in R2 at equality.

## Connection to the shipped files

The artifact is exactly **96,558 bytes**, SHA-256:

```text
e39434314a9eb0399edf943c6a0475d34ff9d0d7ec0bb4a1b8ba726b4a6a88fb
```

`check.py` checks this fixed digest and size, verifies all hashes in
[verification/inputs.sha256](verification/inputs.sha256), and validates the
module using `wasm-tools`. It builds a WAST script containing **all original
binary bytes**, then invokes the original `calc_cpm_raw` through Wasmtime.
It does not rebuild C, extract/rewrite a function, or replace its arithmetic.

The host environment is generated from the artifact's 151 imports. It provides
32 pages of memory, a nine-entry function table, imported globals (zero except
the stack pointer at 131072), zero-initializing allocation starting at 262144,
and a free operation that retains the short-lived allocation. All other
imported functions trap if called. The caller uses addresses 65536–65647,
disjoint from static data, stack, and allocated scratch. Its 32-byte wasm32
`cmx` layout follows `src/edgeR.h`. Library sizes use the repeated-row
representation (`type=2`); output starts with the input counts. This exercises
the artifact's real `get_row` path. There is no replacement for that function.
The raw path uses no dynamic-linker data relocations or constructors; neither
is needed for its dimension loads, scratch allocation, data loads, or floating
operations. These host choices are part of the execution witness, not a claim
about every possible host or invalid ABI input.

For R2, `check.py` additionally runs the same original module through Wasmtime's
CLI to retrieve all four output matrix entries. It checks the returned
binary64 bits before transporting them as 17-digit decimal values to R.
[verification/filter.R](verification/filter.R) sources **both shipped R files
unmodified**, and executes their actual S3 default methods, validation, median,
cutoff, sample-size rule, tolerance, row sums, and final conjunction.

The complete edgeR R package and its native-R-to-Wasm loader are not installed.
The R check therefore supplies two explicit fixture adapters:

* `makeCompressedMatrix` checks this fixture's dimensions and library sizes and
  creates a descriptor; the actual compressed representation is constructed
  by the Wasm caller.
* `.Call` checks the raw-operation symbol, exact input matrix, library
  descriptor, and thread count, then returns the matrix obtained from the
  original Wasm. It performs no CPM arithmetic.

Consequently this is a checked composition of the supplied R code with the
artifact's actual result for this input, rather than execution of an installed
edgeR package inside its production loader. The adapters and ABI setup must
be reviewed for that connection. The Lean model alone does not establish it.

## Exact Lean statements

All declarations are in namespace `Verification` in
[Proofs/Requirements.lean](Proofs/Requirements.lean), imported by
[Proofs.lean](Proofs.lean). `ℚ` means exact rationals; no Lean `Float` calculation
or native evaluator is used in these proofs. The relevant definitions are:

```lean
idealCPM (c L : ℚ) : ℚ := c / L * 1000000
kernelBoundary : ℚ := 1193046471111111 / 2147483648
cutoffQuotient : ℚ := 2501999792983609 / 4503599627370496
cutoffBoundary : ℚ := 4772185884444445 / 8589934592
boundaryULP : ℚ := 1 / 8589934592
maxFinite : ℚ := (2 - 1 / 2^52) * 2^1023

GridCertificate (x y step : ℚ) : Prop :=
  ∃ k : ℤ, y = (k : ℚ) * step ∧ 0 < step ∧
    y - step / 2 < x ∧ x < y + step / 2

keepsTwo (cpm cutoff total : ℚ) : Prop :=
  (2 : ℚ) ≤ (if cutoff ≤ cpm then 2 else 0) ∧ 15 ≤ total
```

`positiveNormal64` decodes a positive normal binary64 bit pattern `b` as
`(2^52 + b % 2^52) * 2^((b / 2^52) % 2048 - 1075)`, with an integer exponent
and rational arithmetic. Its domain restriction is intentional: it is not a
model of NaNs, infinity, subnormals, or negative numbers.

The exact theorem statements, with proof bodies omitted, are:

```lean
theorem witness_encodings :
    positiveNormal64 0x4120f4471c71c71c = kernelBoundary ∧
    positiveNormal64 0x4120f4471c71c71d = cutoffBoundary ∧
    positiveNormal64 0x3fe1c71c71c71c72 = cutoffQuotient ∧
    positiveNormal64 0x7fe0000000000000 = (2 : ℚ)^1023

theorem gridCertificate_nearest {x y step : ℚ} (h : GridCertificate x y step) :
    ∀ z : ℤ, (z : ℚ) * step ≠ y → |x - y| < |x - (z : ℚ) * step|

theorem kernel_rounding :
    GridCertificate (idealCPM 10 18) kernelBoundary boundaryULP

theorem cutoff_division_rounding :
    GridCertificate ((10 : ℚ) / 18) cutoffQuotient (1 / 2^53)

theorem cutoff_multiplication_rounding :
    GridCertificate (cutoffQuotient * 1000000) cutoffBoundary boundaryULP

theorem boundary_errors :
    kernelBoundary - idealCPM 10 18 = -1 / 19327352832 ∧
    cutoffBoundary - idealCPM 10 18 = 5 / 77309411328 ∧
    |kernelBoundary - idealCPM 10 18| / idealCPM 10 18 =
      1 / 10737418240000000 ∧
    cutoffBoundary - kernelBoundary = boundaryULP

theorem r2_counterexample :
    keepsTwo (idealCPM 10 18) (idealCPM 10 18) 20 ∧
    ¬ keepsTwo kernelBoundary cutoffBoundary 20

theorem r2_tolerance_robust (required totalCutoff : ℚ)
    (hr : 0 < required) (_ht : totalCutoff ≤ 20) :
    (required ≤ (if cutoffBoundary ≤ kernelBoundary then (2 : ℚ) else 0) ∧
      totalCutoff ≤ 20) = False

theorem r1_overflow_witness :
    0 < (2 : ℚ)^1023 ∧
    (2 : ℚ)^1023 ≤ maxFinite ∧
    idealCPM ((2 : ℚ)^1023) ((2 : ℚ)^1023) = 1000000 ∧
    (2 : ℚ)^1024 < (2 : ℚ)^1023 * 1000000
```

The midpoint certificates prove strict nearest rounding on the indicated
binary grids; there are no ties. The actual IEEE-754 results are independently
checked by execution. `keepsTwo` is a deliberately small exact comparison
model for two identical samples with the default total cutoff; it is not an
R interpreter. The tolerance theorem covers positive required counts, while
the R check executes the actual binary64 tolerance subtraction.

## Reproduce every result

From this directory, with the installed tools and built Mathlib available:

```sh
python3 verification/check.py
lake build
lake env lean Proofs/Requirements.lean
```

No network is used. All three commands must exit with status zero. The Python
command must print:

```text
Pinned input hashes: PASS
Original-byte Wasmtime assertions: PASS (R1 overflow and R2 boundary)
R1: c=L=0x1p+1023; kernel=+inf; divide-first=1000000
R2 boundary: artifact CPM=555555.5555555555; R cutoff=555555.55555555562
Shipped R wrapper/filter with checked Wasm-result adapter: PASS
R2 documented decision: TRUE,FALSE; actual decision: FALSE,FALSE
All executable counterexamples: PASS
```

The Lean commands must succeed, and the nine `#print axioms` outputs must list
only `propext`, `Classical.choice`, and `Quot.sound` (order may vary). In
particular, no theorem depends on `sorryAx` or an unchecked computation axiom.
The direct `lake env lean` command checks the proof source again even if Lake's
normal build is cached. PASS means that the stated counterexamples were
reproduced, not that the requirements passed.
