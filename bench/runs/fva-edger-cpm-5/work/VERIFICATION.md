# Verification of edgeR CPM and expression filtering

Both requirements, on their stated domains, have counterexamples. This delivery
contains kernel-checked FVA proofs of the relevant **actual Wasm fragment**, plus
reproducible full-function executions and an R filtering demonstration. It does
**not** claim a kernel-checked end-to-end proof of the full C/R application.

## R1: overflow prevents a global finite rounding-error guarantee

Use a one-row, one-column double matrix with count and library size both
`2^1023` (binary64 bits `0x7fe0000000000000`), and `nthreads=1`.
These inputs are finite, positive, exactly representable integers, with `c = L`.
The exact required value is `(c / L) * 1000000 = 1000000`, itself exactly
representable. The shipped `calc_cpm_raw` instead writes positive infinity,
bits `0x7ff0000000000000`.

Its update is `fl(fl(c * 1000000) / L)`: multiplication overflows before the
division. Thus no finite absolute or relative error bound against the finite
exact answer holds for every input in R1. This is an overflow counterexample to
the unrestricted numerical guarantee, not a claim that Wasm's individual
floating-point instructions round incorrectly. No universal error theorem for
a restricted, non-overflowing domain is asserted here.

The exact theorem in `Proofs/Proof.lean` is:

```lean
theorem r1_overflow_holds : r1_overflow
```

Its proposition, defined in `Proofs/Spec.lean`, is exactly:

```lean
def r1_overflow : Prop := artifact_binding ∧
  ∀ H : HostSem, Must H (wrote 9218868437227405312)
    (cellStart 9214364837600034816 9214364837600034816)
```

`cellStart` starts the extracted 13 instructions, through `f64.store`, with a
one-page memory containing the count at address 0 and library size at address
16, and locals pointing to those cells. `wrote bits` requires termination
without a trap, no returned values, and those exact eight output bytes at
address 0. `Must` quantifies over every execution under every host behavior;
the fragment makes no host calls. These are FVA semantic statements, not
evaluations using Lean's native floating-point arithmetic.

`verification/run-wasm.js` and the Wasmtime assertions generated by
`verification/make-wast.py` independently demonstrate the same result by
calling the **whole exported function** on the original binary. A control case
`c=10, L=1000000` returns 10.

## R2: rejection at the stated minimum count

Run the shipped R functions on:

```r
y <- matrix(c(10, 10), nrow=1)
filterByExpr(y, lib.size=c(18, 18), min.sample.size=2)
```

All other tuning arguments retain their defaults: `min.count=10`,
`min.total.count=15`, `large.n=10`, `min.prop=0.7`, `max.n.samples=40`,
and `preset=NULL`. Both library sizes equal their median, so the documented
scaling leaves the count threshold at exactly 10 in each sample. Both samples
reach it; the total count is 20 and passes the documented additional total
condition. The expected count-threshold predicate is TRUE, but the function
returns FALSE.

The cause is a one-ulp discrepancy in the two evaluation orders:

| Quantity | Evaluation | Exact binary64 bits |
|---|---|---|
| Each CPM | `(10 * 1000000) / 18` in the artifact | `0x4120f4471c71c71c` |
| CPM cutoff | `(10 / 18) * 1000000` in R | `0x4120f4471c71c71d` |

The values print as `555555.55555555550` and `555555.55555555562`, respectively;
their gap is exactly `2^-33`, about `1.1641532182693481e-10`. The R code applies
its `1e-14` tolerance to the number of passing samples and the total count,
not to the CPM comparison. Consequently neither sample passes `CPM >= cutoff`.

The exact theorem in `Proofs/Proof.lean` is:

```lean
theorem r2_boundary_holds : r2_boundary
```

Its proposition in `Proofs/Spec.lean` is exactly:

```lean
def r2_boundary : Prop := artifact_binding ∧
  ∀ H : HostSem, Must H (wrote 4693019397977130780)
    (cellStart 4621819117588971520 4625759767262920704)
```

The input naturals encode binary64 10 and 18; the output natural encodes the
lower CPM shown above. The R cutoff and final filtering decision are runtime
assertions in `verification/filter.R`, not Lean theorems about R semantics.
That script sources both shipped R files unchanged and checks FALSE against
an explicitly computed count-threshold predicate of TRUE.

There is also a separate literal mismatch: R2's "exactly when" omits the
documented `min.total.count` condition. For one sample with count 10 and library
size one million, the per-sample criterion passes but the default total minimum
15 rejects the gene. The R script checks this too. That extra condition agrees
with the manual. The two-sample boundary counterexample above passes it and
therefore does not depend on that omission.

These findings concern R2's exact count-threshold equivalence. The code does
implement a comparison of its *rounded* CPM values against its *rounded* cutoff,
followed by the total-count test; that operational reading is weaker than the
unqualified count-threshold equivalence.

## Connection to the shipped files

The binary is exactly `edgeR.so`, 96,558 bytes, SHA-256:

```
e39434314a9eb0399edf943c6a0475d34ff9d0d7ec0bb4a1b8ba726b4a6a88fb
```

`Proofs/Lifted.lean` was generated with:

```sh
lake exe fva lift edgeR.so Proofs/Lifted.lean --ns Proofs.Lifted
```

It stores every byte and proves
`decode bytes len = .ok module` using FVA's decoder in the kernel. It has not
been hand-edited. `artifact_binding_holds : artifact_binding`, the third theorem
in `Proofs/Proof.lean`, proves that the named export has function index 160,
there are 74 imported functions, defined function 86 is its body, and the
extracted update is exactly the instruction list stated in `Proofs/Spec.lean`.
FVA's trust check additionally checks the generated file and exact binary link,
and replays `decode_eq` along with the three claims.

The Lean execution proofs start at the update fragment. They do not prove
reachability from function entry, allocation correctness, matrix traversal, or
R execution. Those gaps are covered by the concrete demonstrations, subject to
the following explicit runtime trust:

* Both runtime harnesses load all original binary bytes; no C recompilation or
  arithmetic replacement is involved. They provide imported memory/table/globals,
  zero-initializing allocation, and no-op frees. Unrelated imported functions
  trap if called. The Node harness additionally checks the exact allocation/free
  call sequence. Neither harness invokes unrelated package constructors.
* Matrices use the 32-bit `cmx` layout in `src/edgeR.h`, with caller-owned output
  initially containing the counts, as the raw-CPM interface requires.
* The complete installed edgeR R package is absent. `verification/filter.R`
  supplies `makeCompressedMatrix` for these vector library sizes and a `.Call`
  bridge that marshals doubles to the actual Wasm function and back. It does not
  reimplement CPM arithmetic or the filtering decision. It exercises the shipped
  `cpm.default` and `filterByExpr.default`, but does not verify the unavailable
  production R-to-Wasm wrapper or other R methods/argument combinations.
* `verification/inputs.sha256` pins the R files, ABI header, requirements, manual,
  and binary used in these demonstrations.

## Reproduce all results

From this directory, with the provided offline dependencies and prebuilt FVA
objects available, run:

```sh
bash verification/check.sh
```

The script checks the input hashes, runs `lake build`, generates a WAST script
embedding the exact artifact, runs it in Wasmtime, runs the Node and R assertions,
then copies FVA outside the project and links its supplied object files there.
The external executable retains the provided embedded base manifest and runs:

```sh
<external-fva> trust . --spec-module Proofs.Spec --root-module Proofs --surface-budget 120
```

Success means exit status 0, a successful Lean build, all three runtime markers
`WASMTIME COUNTEREXAMPLES PASS`, `WASM COUNTEREXAMPLES PASS`,
`R COUNTEREXAMPLES PASS`, and `fva trust: PASS`. A passing audit establishes the
three stated formal claims, including their deliberately limited execution scope;
it does not mean R1 and R2 hold. The audit output is saved to
`verification/trust.txt`; the recorded complete run is `verification/check.log`.

The executable checks can also be run individually:

```sh
sha256sum -c verification/inputs.sha256
lake build
python3 verification/make-wast.py
wasmtime wast -C cache=n verification/full-artifact.wast
node verification/run-wasm.js
Rscript verification/filter.R
```

Wasmtime returns status 0 without output when its assertions pass. Its cache is
disabled to permit running in the provided filesystem sandbox.

Observed result: `bash verification/check.sh` exited 0. FVA reported PASS,
the artifact link matched, and both replay kernels accepted the exported proofs:
`leanchecker` (154 seconds) and the independent `con-leche` (129 seconds).
The review surface reported by FVA is **40 code lines**, all in `Proofs.Spec`.
The only reported proof axioms are the usual `propext`, `Classical.choice`,
and `Quot.sound` (the binding theorem uses only `propext`).

Of 72 known-false canaries, `leanchecker` rejected 71 and accepted the documented
replaced-prelude canary listed in FVA's `trust/canaries/known.tsv`.
`con-leche` rejected 69, declined 3, and accepted none. Neither kernel crashed
or timed out. The PASS therefore includes FVA's documented official-prelude
assumption and canary policy; it does not assert that every kernel rejected
every canary.
