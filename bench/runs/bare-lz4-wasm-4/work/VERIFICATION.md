# Verification result

**R1, R2, and R3 all fail.** Each has a concrete counterexample executed
against the shipped binary. Lean proves the format facts used to classify
those examples. There is no claim of a universal correctness proof or of a
formalization of WebAssembly execution.

## Artifact and connection to the results

The artifact tested is `lz4-block-codec.wasm`, exactly 1,226 bytes, SHA-256:

```text
4bda6947a0498618552cba53ab3780745fd34cc1a0d84696e83a0547dcd68acf
```

`verification/check.py` checks both size and hash, validates the binary, then
embeds **all its original bytes** in each WAST script as a `module binary`.
It registers that module as `codec`. The test wrappers import its exported
memory and functions; they do not reimplement or modify the codec. Each case
uses a fresh instance. Wasmtime checks every `assert_return` and `assert_trap`.
The generated scripts are temporary and are reproducibly regenerated by the
checker. Neither the hand-written `.wat` nor a recompilation of it is used.

The Lean file `Proofs/Counterexamples.lean` defines a separate executable model
of the supplied `lz4_Block_format.md`: token nibbles, extension bytes,
little-endian nonzero offsets into previous output, sequential overlapping
match copies, literal-only termination, and the three end conditions. It
uses natural numbers and byte lists, with a byte-range check. Its sequence
fuel is the compressed length plus one; each recursive sequence consumes
at least three bytes. This is a transcription of the format for checking
these witnesses, not a proved equivalence to the prose or a model of the
codec. The connection between its concrete byte lists and the runtime test
vectors is visible in the two files and must be reviewed.

## R1: encoder produces an invalid block

Input is the 13 ASCII bytes `abcdabcd12345`:

```text
61 62 63 64 61 62 63 64 31 32 33 34 35
```

The wrapper grows memory to five pages, fills all 65,536 four-byte hash-table
entries in `[0,262144)` with `-65536`, and places the input at `262144`, just
after that table. It calls `lz4BlockEncode(262144, 13, 262208)` with disjoint
buffers and sufficient space (`lz4BlockEncodeBound(13)` is checked to be 29).
The original artifact returns **13** and writes exactly:

```text
40 61 62 63 64 04 00 50 31 32 33 34 35
```

`R1_late_match` checks the returned length and all 13 output bytes. These
sequences are four literals `abcd`, an offset-4 match of length 4, and five
final literals `12345`. They reconstruct the input, but the match starts
at decoded position 4 of 13. Only nine bytes remain: `4 + 12 > 13` violates
end condition 3. Thus the validity conjunct of R1 fails, independently of
whether a permissive decoder accepts this output.

Exact Lean statements, all in namespace `LZ4` in
`Proofs/Counterexamples.lean`:

```lean
theorem r1_parse : parse r1Block = some ⟨r1Input, 5, [4]⟩
theorem r1_invalid : ¬ ValidBlock r1Block
theorem r1_match_too_late : ¬ (4 + 12 ≤ r1Input.length)
```

Here `r1Input` and `r1Block` are exactly the two byte lists above. The source's
inner match-finding loop can search beyond the outer loop's `end - 12`
threshold, explaining the failure; that explanation is not needed as an
assumption of the runtime test.

## R2: a valid block decodes to the wrong result

The 10-byte input block is:

```text
13 61 01 00 50 62 63 64 65 66
```

Its content is `aaaaaaaabcdef` (eight `a` bytes followed by `bcdef`), 13 bytes:

```text
61 61 61 61 61 61 61 61 62 63 64 65 66
```

It contains one literal, an offset-1 match of length 7, and five final
literals. Its only match starts at position 1, exactly 12 bytes before the
end. All format end conditions hold, including correct overlapping copying.

The wrapper places the block in `[1024,1034)` and initializes `[0,13)` with
13 ASCII question marks. Both buffers are within the initial one-page
memory and are disjoint. `lz4BlockDecode(1024, 10, 0)` returns **1**, leaving
`a????????????` in the 13-byte output area. `R2_early_return` checks that
return and every output byte. The interface does not require the output to
follow the input in memory.

The decoder compares the computed match source address (0 here) against
the **compressed input end** (1034), and exits early. The comparison should
not reject this legal output layout.

Exact Lean statements in `Proofs/Counterexamples.lean`:

```lean
theorem r2_parse : parse r2Block = some ⟨r2Content, 5, [1]⟩
theorem r2_valid : ValidBlock r2Block
theorem r2_expected_length : r2Content.length = 13
theorem r2_return_wrong : (1 : Nat) ≠ r2Content.length
```

`r2Block` and `r2Content` are exactly the byte lists printed above.

## R3: reading beyond a valid empty block

Input block is the single byte `00`, the representation of empty input
explicitly permitted by end condition 2 of the supplied format document.
Place it at address **65535** in the module's initial one-page memory and
call `lz4BlockDecode(65535, 1, 0)`. The entire input is in bounds, and the
expected decoded content and length are empty and zero.

`R3_empty_overread` checks that memory has one page and that the call traps
with **`out of bounds memory access`**. After consuming the token, the
decoder's zero-literal path skips the end-of-input check and attempts its
first offset-byte **load at 65536**, outside both `[65535,65536)` and memory.
There is no literal copy or output store before that load. The trap is not
caused by an undersized output buffer. This is an input read, not a normal
match read from previously decoded output. The decoder function (function
index 3) in `wasm-tools print lz4-block-codec.wasm` shows this path directly.
The trap also supplies another counterexample to R2.

Exact Lean statements in `Proofs/Counterexamples.lean`:

```lean
theorem empty_parse : parse [0] = some ⟨[], 0, []⟩
theorem empty_valid : ValidBlock [0]
theorem empty_block_fits : (65535 : Nat) + [0].length = 65536
theorem empty_offset_outside :
    ¬ ((65536 : Nat) < 65535 + [0].length) ∧ ¬ ((65536 : Nat) < 65536)
```

The last theorem establishes address arithmetic, not a formal execution
trace. The executed trap and inspection of the binary decoder identify
the attempted read.

## Reproduction

Run from this directory, without network access:

```sh
lake build
lake env lean Proofs/Counterexamples.lean
python3 verification/check.py
```

Success means every command exits with status 0. `lake build` reports
`Build completed successfully`. The direct Lean command prints the axiom
sets for all eleven theorems: either no axioms or only `propext`; there is
no `sorryAx` or additional assumed correctness axiom. Proofs use `decide`
and kernel-checked rewriting, without `native_decide`.

The Python command prints:

```text
PASS artifact: 1226 bytes, sha256 4bda6947a0498618552cba53ab3780745fd34cc1a0d84696e83a0547dcd68acf
PASS R1_late_match
PASS R2_early_return
PASS R3_empty_overread
All three requirements have reproducible counterexamples.
```

Here **PASS means the advertised failure was reproduced**, not that the
requirement holds. Any mismatched byte, return value, expected trap, artifact
hash, or validator failure makes the checker exit unsuccessfully.
`-C cache=n` prevents Wasmtime from needing a writable user cache.

Optional binary inspection:

```sh
wasm-tools print lz4-block-codec.wasm
```

Checked with Lean 4.35.0, Mathlib v4.35.0, Wasmtime 50.0.0
(`ebe5e8df1`), and wasm-tools 1.262.0 (`e22db44da`).

| `lz4-block-codec.wasm` | binary | 1226 | Executed artifact; inspect decoder instructions for R3 read attribution |

The trusted proof base is Lean's kernel and the reported standard axiom
`propext`, together with the adequacy of the format definitions for the
prose specification. Mathlib tactics construct checked terms. The runtime
demonstrations additionally trust Python and its standard library, Wasmtime's
WAST assertions and WebAssembly execution, and wasm-tools validation. These
external tools are not verified here. The Python harness and its connection
to the Lean constants are not formally proved correct; they are the small
explicit executable witness checker a reviewer must audit.

The hand-written `lz4-block-codec.wat` (745 lines, 21827 bytes) is explanatory
source only; no source/binary equivalence is assumed. There are no remaining
unresolved requirements in the sense of CHECK.md: each of R1–R3 has a
counterexample. No conclusions about other inputs or unlisted API properties
follow from this verification.
