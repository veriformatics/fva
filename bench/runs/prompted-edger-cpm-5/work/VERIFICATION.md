The requested universal accuracy/equivalence claims have reproducible counterexamples. The delivered results consist of executions of the shipped artifacts, plus exact arithmetic certificates replayed by two proof kernels. The kernels certify the arithmetic certificates; the execution results rely on the runtimes and the small harnesses described below.

Run this single command from this directory, with no network:

```sh
python3 verification/check.py
```

Success means exit status 0 and the final line:

```text
ALL CHECKS PASSED: requirement counterexamples reproduced; certificates accepted by two kernels; negative controls rejected.
```

“Passed” means that the counterexamples and checking controls worked. It does not mean that R1 and R2 hold. Detailed generated certificates, WAST, dependency lists, and logs are in `.verification/` and are recreated by the command. The command always recompiles `Proofs/Arithmetic.lean` from source before exporting its proofs.

**R1: unavoidable qualification of the numerical claim.**

Use a 1×1 matrix with finite, nonnegative, exactly representable `c = L = 2^1020`, and `nthreads = 1`. Initialize the in-place output buffer with `c`, as the C interface requires. Both V8 and Wasmtime run the original exported `calc_cpm_raw` and return positive infinity, bits `0x7ff0000000000000`. The requested real value `(c/L)*1000000` is exactly `1000000`, which is itself exactly representable in binary64.

The binary performs `f64.mul` by 1000000 before `f64.div` by L. Its intermediate product exceeds the round-to-nearest overflow boundary `2^1024 - 2^970`. Thus there is no finite absolute or relative error bound for all of the finite inputs allowed by R1: this witness has infinite error relative to a finite exact answer. This is avoidable intermediate overflow, rather than an unrepresentable final mathematical answer.

The exact certificate `Verification.r1_exact_and_overflow` is in `Proofs/Arithmetic.lean`. Its full statement is reproduced below. The concrete execution assertions are in `verification/wasm.mjs` and in the WAST generated by `verification/wast.py`.

Interpretation matters: if “as double-precision arithmetic allows” deliberately permits intermediate overflow even when the requested final answer is representable, this witness establishes an accuracy limitation under that interpretation. It refutes an unconditional finite-accuracy claim and the divide-then-scale evaluation order. No general theorem for a restricted, overflow-free domain is claimed.

**R2: exact count-threshold equivalence fails.**

The first input uses ordinary integer counts and every default filtering parameter:

```r
y <- matrix(c(10,8,10,8), nrow=2, ncol=2)
#          sample1 sample2
# gene1       10      10
# gene2        8       8
filterByExpr(y)
```

There is one group containing both samples. Library sizes default to `colSums(y) = c(18,18)`; the median is 18 and the required sample count is 2. Gene 1 reaches `min.count = 10` in both samples. It also meets the separately documented `min.total.count = 15`, since its total is 20. Exact arithmetic gives the same CPM for the count and its cutoff. Nevertheless, the observed result is `c(FALSE,FALSE)`.

| Quantity for gene 1 | Binary64 bits | Exact rational value |
|---|---|---|
| Wasm CPM, `(10*1000000)/18` | `0x4120f4471c71c71c` | `4772185884444444 / 2^33` |
| R cutoff, `(10/18)*1000000` | `0x4120f4471c71c71d` | `4772185884444445 / 2^33` |

The values differ by one ULP, `2^-33`. The CPM's signed error from the exact target `10000000/18` is exactly `-1/(9*2^31)` (about `-5.174e-11`). `Verification.r2_rounding_intervals` certifies the strict nearest-rounding intervals for all three floating operations involved, the ordering of the results, equality of the real formulas, satisfaction of the total-count condition, and these exact error/gap values. All candidates are positive normal binary64 numbers away from binade boundaries; no halfway ties occur.

This counterexample addresses the README's exact count-based equivalence with median-library scaling. For this input the implementation does follow the operational rule “compare the computed floating CPM to the computed floating cutoff”; that operational rule differs from the exact count-based rule at the boundary.

There is also an independent counterexample to the documentation's exact sample-number condition, with CPM values far from the cutoff:

```r
y <- matrix(c(20,0), nrow=1)
filterByExpr(y, lib.size=c(1e6,1e6), min.sample.size=1+2^-48)
# TRUE
```

Exactly one sample has CPM ≥ 10. The required number is `1.0000000000000036`, so the literal “at least the required number” condition fails. The total is 20 ≥ 15. Neither the large-group adjustment nor the cap applies. The implementation subtracts `tol = 1e-14` before comparing the sample count, and therefore keeps the gene. `Verification.r2_fractional_sample_threshold` proves the exact rational inequalities explaining this tolerance window; the R assertion checks the actual floating execution. The theorem's decimal tolerance is the exact rational `1/10^14`; the execution test covers R's binary64 representation and subtraction.

Both R examples are executed by `verification/filter.R`, which sources the two original R files unchanged, registers their actual S3 methods, and calls their generics. All filtering, median, matrix operations, comparisons, defaults, and parameter handling execute in R. The missing edgeR compression/FFI helpers are supplied by a small adapter: it expands the library-size vector, sends the matrix to the Node process, calls the original Wasm `make_cmx` and `calc_cpm_raw`, and returns the output matrix to the shipped `cpm.default`. CPM arithmetic is performed by that binary.

**Exact formal statements and definitions.**

The namespace is `Verification`. The only local definitions on which the theorem statements depend are:

```lean
def dyadic (m d : Nat) : Rat := mkRat (Int.ofNat m) (2^d)

def nearest (x : Rat) (m d : Nat) : Prop :=
  dyadic (2*m-1) (d+1) < x ∧ x < dyadic (2*m+1) (d+1)
```

The three complete theorem types are:

```lean
theorem r1_exact_and_overflow :
    let c : Rat := (2^1020 : Nat)
    let maxFinite : Rat := (2^1024 - 2^971 : Nat)
    let overflowBoundary : Rat := (2^1024 - 2^970 : Nat)
    0 < c ∧ c ≤ maxFinite ∧ c / c * 1000000 = 1000000 ∧
      overflowBoundary < c * 1000000

theorem r2_rounding_intervals :
    nearest ((10 : Rat) * 1000000 / 18) 4772185884444444 33 ∧
    nearest ((10 : Rat) / 18) 5003999585967218 53 ∧
    nearest (dyadic 5003999585967218 53 * 1000000) 4772185884444445 33 ∧
    dyadic 4772185884444444 33 < dyadic 4772185884444445 33 ∧
    (10 : Rat) / 18 * 1000000 = (10 : Rat) * 1000000 / 18 ∧
    (15 : Nat) ≤ 10 + 10 ∧
    dyadic 4772185884444444 33 - (10000000 : Rat) / 18 =
      -mkRat 1 (9 * 2^31) ∧
    dyadic 4772185884444445 33 - dyadic 4772185884444444 33 = dyadic 1 33

theorem r2_fractional_sample_threshold :
    (1 : Rat) < 1 + dyadic 1 48 ∧
    1 + dyadic 1 48 - mkRat 1 (10^14) < 1
```

Their proof bodies use `decide +kernel`, with `unfold` for the two definitions where needed. They use Lean's exact `Rat`, `Int`, and `Nat` operations. There is no floating-point oracle, `native_decide`, added axiom, or `sorry` in these proofs. `nearest` expresses a rational midpoint interval; the standard IEEE-754 interpretation of that interval and of the overflow boundary is part of the reviewed numerical interpretation, rather than a formalized Wasm semantics theorem.

**Connection to the shipped bytes and checking independence.**

`edgeR.so` remains 96,558 bytes, SHA-256:

```text
e39434314a9eb0399edf943c6a0475d34ff9d0d7ec0bb4a1b8ba726b4a6a88fb
```

`verification/artifacts.sha256` pins the original README, CHECK, C sources, R sources, documentation, binary, and Lake configuration. Every check begins by verifying those hashes. The implementation sources and binary were left unchanged.

The Node harness instantiates the exact binary. The WAST generator embeds every original byte using WAST's binary-module form; it retains all functions, imports, data, and the start function. It does not recompile the C, extract and replace the arithmetic, or instantiate a rewritten numerical kernel. Both runtime tests call the shipped `make_cmx` constructor and then `calc_cpm_raw`, including the real loops, strides, `get_row`, loads, stores, and floating operations. Both check the full 2×2 result as well as the overflow cell.

The host provides disjoint linear memory, the imported globals/table, a zero-filling bump allocator implementing `R_chk_calloc`, and `R_chk_free` as a no-op for these short executions. Other function imports trap if called. Static data, input buffers, heap, and stack are disjoint. This harness establishes the concrete direct-C-interface executions under that allocator/ABI; a complete R-universe dynamic loader and the rest of R's C runtime are outside this check.

The proof exporter includes the transitive dependency closure of the three target certificates. The default C++ Lean kernel (`leanchecker --from-export`) and the independently implemented Lean4Lean kernel (`lean4lean --import`) each replay that exported environment from an empty environment. Library proof bodies are included. The audit checks that all three target theorems are present and that the only axioms anywhere in the export are `propext`, `Classical.choice`, and `Quot.sound`. It also rejects `sorryAx` and native-reduction shortcuts.

The check constructs two well-formed export files with genuinely ill-typed proofs: `True.intro : False`, and `Eq.refl 0 : 0 = 1`. Each must be rejected by each kernel with a declaration-type-mismatch diagnostic naming the injected declaration. An arbitrary nonzero exit, timeout, missing file, or parse failure does not count. Lean4Lean's installed CLI emits pretty-printer panic diagnostics while reporting these expected errors; the logs also contain the kernel's explicit type mismatch and exit status 1, which the driver requires.

A third negative inserts an explicit axiom of `False`, which the axiom audit must reject. This matters because kernels permit assumptions. Runtime negatives assert the false results “overflow cell returns 1000000”, “CPM equals zero”, and “the boundary gene is retained”; Wasmtime, the Node assertions, and the R assertions must reject those respectively. Positive checks run before all negative controls.

Installed versions used: Lean 4.35.0, Wasmtime 50.0.0, wasm-tools 1.262.0, Node 26.11.1, R 4.6.1. R's installed `jsonlite` is used for the FFI data transfer. No Mathlib theorem is needed; using only core rational arithmetic keeps the certificate closure smaller. The Lake dependency on Mathlib remains unchanged.
