# U10 contract — `fva explain` (tier: shallow, advisory)

Purpose: the prototype Decision "Non-expert review aid" rebuilt Lean-native (Decisions: Stack, Non-expert review aid). Advisory: the verdict stays with `fva trust`; a wrong explanation misleads a reader but never changes a verdict, and the examples' values never come from the model.

## Behavior (from the Decisions entry)
- X1 Proof status per claim = issues of a fresh `fva trust --json` naming the claim or its proofs (whole-name match) + the project-wide ones naming no claim; never saved.
- X2 Pass 1 (`codex app-server`, ephemeral read-only thread, `outputSchema`) explains each claim from the comment-stripped review-surface source + its elaborated statement + FVA's claim vocabulary (`FVA/Spec/CAbi.lean`, `FVA/Spec/Claims.lean`), every project name neutral (D5: `FVA.Tool.Explain.Renamer`: a review-module constant's last component → `claim_k`/`name_k` wherever an identifier names it; strings, projections, other packages' names kept; reply text renamed back). Pass 2 with a requirements file (`requirements.md` beside the spec or `--requirements`; `## <id>` per requirement, leading text = context): per requirement, the claims stating it (neutral names, statements, explanations, computed examples; no docstring) → `matches|weaker|stronger|different|vacuous|missing`; without one: each claim's explanation + examples vs its docstring, else its name → `matches|weaker|stronger|different|vacuous`.
- X3 Examples for claims `∀ (x : BitVec n)…, Returns m "f" args res` about one lifted subject: inputs = pass 1's proposals + `0`, `1` per argument (mod 2^bits, deduplicated, at most 8); spec value = `res` reduced by `whnf` (D16: definitional, so an `implemented_by` override cannot change it; compiled code never runs) and confirmed by the kernel (`res = value` by `rfl` through `Kernel.Environment.addDecl`; a refusal shown as such; `FVA.Explain.run` under `lake env lean`; D17: each case's reduction and kernel check get `FVA.Explain.caseHeartbeats` = 10000 (thousands of heartbeats, deterministic), past it = too costly, decided inside Lean (`sum_to(4294967295)` ≈ 1 s), the process timeout only a backstop); only confirmed values reach pass 2; binary value = `wasmtime run --invoke` on the subject's `.wasm` (signed arguments, results mod 2^bits, a trap shown). D18 adds two shapes (`FVA.Explain.shape`): `∀ inputs outputs, Returns m "f" args [outs] → φ` (rows: inputs → the binary's results (wasmtime) put for the output variables → `φ` decided) and a decidable `∀ inputs, φ` (rows: inputs → `φ` decided); `decide φ` reduced by `whnf` and confirmed by the kernel within the case budget (`FVA.Explain.decideCases`); a trap = "the claim says nothing for these inputs". Other shapes print their elaborated statement.
- X4 Saved beside the spec module (`fva-explain.json`: model text + examples + verdicts + `inputsSha` + generation time); a rerun shows it without a model call, `--force` regenerates. `inputsSha` = model, effort, prompts, schemas, the requirements file, fixed inputs + caps, review-surface files, the subjects' `Lifted.lean` (numeral = `.wasm` bytes), the vocabulary files, `FVA/Explain.lean`; a mismatch or another claim set → STALE banner.
- X5 rc 0 = trust PASS ∧ text current ∧ every requirement (requirements mode) or else every claim's intent check `matches`; 1 otherwise; 2 usage/setup (incl. a requirements file without `## <id>`). `--json` = the same result as JSON. A project that does not build (trust `[build]`) and has no saved text → the FAIL proof-check line and rc 1, no model call (D63); a saved text still shows, with every claim unproven.

## Evidence (E)
- E1 `scripts/test-trust` runs `fva explain` on the three examples (saved text, no model call; it runs `fva trust` itself): rc 0 each.
- E2 `FVATest.Explain` guards: staleness, proof-status matching (whole names), report text helpers, comment stripping (Lean's tokenizer, shared with the D11 line counter).
- E3 Generated once with the model: every example claim `matches`; spec and binary values agree on every computed case.

- E4 (D15) verdict stability, cohort 1 (scientist-1 design, frozen before the runs; `scripts/explain-stability`; records `docs/explain-stability/cohort-1*`, raw prompts + replies in the archive): started at commit 02b0f15 with the recorded executable + harness hashes; ten fresh generations of each of five fixed examples (Toy, Mem, Rust, Mislabeled, Planted), gpt-6-luna medium both passes; claude-opus-5-5 medium (`claude -p --bare`, no tools) judged each run's identical captured pass-2 payload. The cohort met the D15 thresholds: Toy R1–R3 `matches` 30/30; the five planted negatives non-`matches` 50/50; all 16 targets ten verdicts per backend. GPT false alarms: Mem `arraySum` 3/10 and the honest Planted `sumToSpec` 2/10; the ambiguous Rust `clamp` gave 8 `matches`, 2 `stronger`; rejection labels varied as recorded. Claude returned the preferred gold label on all 150 determinate target-runs and `matches` on all ten ambiguous Rust-clamp runs (the ordered-case reading). A rebase ran during round 3 (executable unchanged; archived formal inputs unchanged within each project); projects ran in parallel within rounds; Claude always ran after GPT. Paired configuration results on known fixtures, not a model-family effect or a low-error guarantee: zero errors in ten runs leaves a one-sided 95 % upper error limit of 25.9 % per target; labels do not certify every explanation.
- E5 (D64) label definitions: `weaker` = part of what the requirement (intent) says and nothing contrary; `different` = for some input a result the requirement rules out, or something else. Cohort 2 (`docs/explain-stability/cohort-2*`, same design and harness as cohort 1, ten rounds): gpt Mislabeled R1 DIFFERENT 10/10 (cohort 1: 7/10, 3 WEAKER); every target's binary gold (matches vs reject) no worse (Mem arraySum 10/10 vs 7/10, Planted sumToSpec 10/10 vs 8/10, clampSpec preferred DIFFERENT 10/10 vs 6/10); one preferred label lower: Planted sumBelowTen VACUOUS once (9/10 DIFFERENT vs 10/10, still a reject); Claude 160/160 at the preferred label. The saved explanations were regenerated under the new prompts (each test-trust pin met; Rust needed 2 generations, the others 1).
