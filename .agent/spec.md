## Intent

FVA (Formally Verify Anything) aims to follow a software development tooling trend brought on by REA (Reverse Engineer Anything): https://github.com/morluto/rea. Our goal is to allow a user to apply FVA to any pre-existing or new project and find a path towards formal verification of it. It is important that the formal verification is directly linked to the code of the software's actual implementation, for instance Verus is tightly integrated with Rust, and Lean allows for metaprogramming. For other languages, we may have to develop our own solutions and it is best if we can find a unified approach to avoid an excess of language-specific handling, which is likely to be brittle and inelegant in approach.

Like REA, FVA should be readily usable by an AI agent that requests it, and that is the primary target. FVA uses extensive AI-generated proofs to achieve its verification claims. At the same time FVA should aim to minimize the surface of human-reviewable spec. This is treated as an optimization problem: provided a minimally sufficient spec, and a trusted kernel like that of Lean's, we can assume that an unbounded amount of proofs can be used to verify correctness of a program. See https://github.com/schildep/verified-3d-mesh-intersection, for an excellent example of this approach. Spec review may be further simplified by informalization back into natural language (https://github.com/metareflection/claimcheck); we must be open to considering alternative and supplementary approaches at all times.

Proof writing alone is not what FVA adds: a capable agent can already write and check proofs when it is asked to verify a project. FVA adds what such an agent does not supply on its own. It keeps the human-reviewable spec small, and it measures that spec as its main result. It does not trust a single checker: it replays proofs through independent kernels and tests each checker against known false proofs. It links the proofs to the real implementation without a rewrite of the source. It verifies the compiled artifact, or, for components that are not practical to verify as programs (compilers, interpreters, code generators, AI pipelines), it certifies each output that they produce.

FVA also uses fvapi, our formal verification API, when the private fvapi library can speed up the work. FVA checks each answer from fvapi itself, and `fva trust` gives the verdict.

## Decisions

- Public artifact edition = `bench-runs-v2-redacted-v1`; source/input bytes + scientific values preserved, machine labels redacted recursively; original evidence retained offline. U33 privacy amendment binds export/pin migration; no regrading or research restart.

- Privacy: historical machine-specific identity + path labels are redacted; scientific source + results remain unchanged. Rewritten history (user ruling): tracked files cite each commit by its new id (a commit outside the rewritten history keeps its old one); no old→new map is published; commit messages keep their old ids.

- Link path = WASM lift: any source language → wasm (compiler + source untrusted) → `fva lift` → `Lifted.lean` = the `.wasm` bytes as one little-endian `Nat` literal + length + readable `module` value + `decode_eq : decode bytes len = .ok module` by `decide +kernel` (Lean decoder evaluated by the kernel ⇒ no lifter trust; structural equality hand-written, since `deriving DecidableEq` rejects the nested `Instr` type); theorems quantify over `module`; the `.wasm` = the verified artifact, committed; `fva trust` checks literal = file bytes + `decode_eq`'s type + kernel replay.
- Trusted base = Lean kernel + axioms {propext, Classical.choice, Quot.sound} + Mathlib at the pinned rev (user ruling: trusted) + FVA's reviewed-once Lean specs, shared across every project/language: Wasm syntax, binary grammar (declarative relation the decoder is proven against), execution semantics (integers, IEEE-754 floats, memory, tables, globals, calls), memory-access footprint (`Reads`/`Writes` = the successful guest load/store a step performs; `Within`, `Throughout`, `CallWithin`), C-ABI vocabulary, verdict spec. Difftest vs wasmtime + the official Wasm spec suite = evidence for the specs, not proof.
- Claims = `@[fva_claim]` defs in `<Lib>/Spec.lean` (D13: `FVA.Spec.ClaimAttr`, reached through `FVA.Lifted`; unmarked `Prop` defs = vocabulary, listed apart in the report, never a FAIL; a theorem in the spec = `[layout]`); proofs = theorems typed by the claim constant, downstream in `<Lib>/Proof.lean` (never read); `<Lib>/Lifted.lean` generated. Spec imports reviewed modules alone; the reverse layout (spec importing proofs) lets unreviewed macros/notation change spec meaning.
- Human-review surface = every module in the spec module's import closure minus Lean core, Mathlib, FVA base + subject, read whole (code lines counted); statement closure reports which subject/base/core names the claims use. Core = by `.olean` origin (Lean sysroot); Mathlib = by origin in the pinned Mathlib package; FVA base = vendored sources whose content hashes match the set the CLI pins; never by module name.
- Distribution: `fva init` vendors the pinned FVA Lean package into each project + requires Mathlib at FVA's pinned rev, oleans from its cache (works offline once fetched, inside `lake check`'s sandbox + in history-free exports).
- Repository contents (user rulings): third-party artifacts + benchmark archives stay out of the repo, fetchable for anyone reproducing the examples or benchmarks; home = `veriformatics/fva-artifacts` releases (files unchanged, sha256-pinned by the fetch scripts, licenses + corresponding source in each release's notes; GPL sources kept there as long as history distributes the bytes). Covered: the archived bench runs, third-party subject builds (lz4-wasm codec, lz4 C/Rust, GLM, runorm) + their lifted modules, FVA-built examples linking third-party code (CppEH, bustools) = rebuilt by script from pinned sources + toolchains, emitted-byte hash checked. FVA's own hand-written fixtures without third-party code (Examples, Cheats, Certs, WasiExit, Tmm certificate data) stay committed as test inputs. Examples + benchmarks use `fva` generally: their specific workflows = scripts beside `fva`, never `fva` functionality. FVA stays Apache-2.0 (GPL aggregation: a relicense would push GPL onto every `fva init` project).
- `fva trust` FAIL on: unproven claim, non-standard axiom (incl. `sorryAx`, `native_decide` + `bv_decide` aux axioms), syntax extension or initializer in a review module (initializers: subject modules too), a command that runs code or changes elaboration in a review module's source (`#eval`, `run_cmd`, `#exit`, `set_option`, `include_str`, code-registering attribute names, interpolated terms: the lists in `FVA/Spec/Trust.lean`), an instance or coercion of a declared Lean-native subject in a claim's statement (outside a subject function's arguments; `Decidable` exempt), `implemented_by`/`extern`/`unsafe`/`partial`/`opaque` in the non-core closure, a claim not mentioning a subject, lifted literal ≠ file bytes or `decode_eq` missing/mistyped, kernel replay rejection (`leanexport` → `lake check --from-export`; `--paranoid` adds every bundled kernel; per-checker status read directly, since Lake labels any nonzero rc `rejected` and nanoda rejects by panic). `lake build` success alone proves nothing (accepts sorry, axioms, kernel bypass).
- Project code runs sandboxed (D12): `fva trust` + `fva explain` run the project's Lake config, build, `lake env` and in-project evaluation, plus the exporter, in bwrap (`/` read-only, home covered, no network, no new user namespace (bwrap < 0.8 or setuid: noted, the rest kept), writable = the `.lake` dirs + the caller's temp dir; an outside `packagesDir`'s packages read-only, D66); the project must carry `lake-manifest.json`. FVA's collector still imports the project's `.olean`s in-process (D62).
- Stack (user ruling): Lean-native, no Python: one Lean 4.35 Lake package on Lean core + Mathlib (user ruling: Mathlib trusted, usable in FVA's core and elsewhere; no other external Lean deps) = specs + proven verdict path + proof library + CLI (`lake exe fva`) + harnesses (Lean + bash). Rust + Verus rejected: FVA's own verdicts would rest on Z3 + Verus's VC generator, which no independent checker re-checks. Talos (AGPL-3.0 Lean Wasm) = reference only.
- Self-verification (user ruling): FVA verifies itself to the greatest extent possible. Boundary table, shipped in the trust report + README: spec (reviewed once) / verified implementation (proven against a spec: decoder sound + complete for the supported profile + grammar unambiguous, verdict function, closures, checker-output parser, certification checkers) / trusted glue (Environment fact collection, IO orchestration, external checker binaries: small, tested, canaried) / residual trust (Lean kernel cross-checked by 5 independent checkers, Lean compiler, the specs).
