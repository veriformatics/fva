# Deferred

One row each: finding → acceptance check.

- D1 Semantics subset too small for real code: no linear memory, `call`, globals, `br_table`, multi-value/typed blocks, `clz`/`ctz`/`popcnt`/`rotl`/`rotr`, floats, imports. → `fva lift` + `fva difftest` succeed on a clang `-O2` program exercising each (array sum over memory, recursive call, switch), with 0 mismatches over ≥1000 cases.
- D2 Lifter (`src/fva/lift.py`) sits in the trusted base. → decoding moves into Lean (`decode : ByteArray → Except String Module`, proven or kernel-evaluated on the pinned bytes), `fva trust` trustedBase lists no Python lifter, and cheat 1 (tampered lift) still FAILs.
- D3 Difftest token `trap` covers both trap and out-of-fuel. → Lean side reports `trap` vs `fuel` separately; a planted non-terminating semantics bug reports `fuel`, never agreement with a wasmtime trap.
- D4 `lake check` sandbox cannot resolve the `../../lean` path dependency, so replay checks our own export, not a sandboxed build. → FVA Lean package consumable from inside a project (vendored copy or git require); `lake check` rc 0 in `examples/toy` without `--from-export`, rc 1 in `examples/cheat`.
- D5 `fva explain` intent = spec author's own docstring/name → round trip checks the claim against its author, not the user. → requirements file (user-written or agent-drafted from source/README/issues, user-approved) as pass-2 intent + identifiers renamed neutral in pass 1; a spec whose docstring + name both say "clamp" but whose body returns `x` still gets `different` when the requirement says clamp.
- D6 Agent packaging absent (Intent: REA-style agent use). → MCP server exposing lift/trust/difftest + an agent skill; an agent session with only the MCP tools verifies a new C function end to end.
- D7 Unified-path evidence covers one source language. → Rust `#![no_std]` clamp/gcd compiled to wasm32, lifted, same `Toy.Spec`-shaped claims proven; report shows identical trusted base.
- D8 Lean-native subjects (mesh-repo style, implementation written in Lean) unsupported by link check: `fva trust` requires a lifted module. → `--subject <Lean module>` path that skips re-lift but enforces override audit; `fva trust` on schildep/verified-3d-mesh-intersection reports a surface within ±10 % of its stated 93 lines.
- D9 Symbolic execution scales unknown: `wasm_sim` on 11-instruction bodies runs in ~1–2 s. → benchmark on a ≥200-instruction function; proof check time recorded; if superlinear, switch to a verified step-function evaluator (`decide`/`cbv`) per straight-line block.
- D10 Statement closure treats every Lean core definition as trusted (e.g. `BitVec.slt`, `Nat.gcd`). → report flags core definitions whose meaning a reviewer must know, with their docstrings, in the review surface section.
- D11 `fva trust` counts `--`/`/-` inside Lean string literals as comments (`project.code_lines`). → line counter uses Lean's own tokenizer (or comment ranges from the parser); a spec line `def s := "--x"` counts as code.
- D12 `fva trust` runs `lake build` with the project's own lake config, outside any sandbox. → build + export run inside `bwrap` (as `lake check` does) with the FVA package mounted read-only; a lakefile `script`/`extern_lib` that writes outside the project fails.
- D13 Claim = any `Prop`-typed def in the spec module, so a helper predicate there reads as an unproven claim. → explicit `@[fva_claim]` attribute (declared in the FVA base) marks claims; unmarked `Prop` defs count as vocabulary; cheat suite still 7/7.
- D14 Kernel replay defaults to Lean's kernel; independent kernels run only under `--paranoid` (+~30 s on toy). → measure on a 10× larger example; if ≤ 2× the default replay time, make `--paranoid` the default.
- D15 `fva explain` verdict stability unmeasured beyond a few runs; one model for both passes (Claimcheck: structural separation across models +10 pts). → ≥10 runs per example claim recorded (toy all `matches`, cheat 5 non-proof-only claims never `matches`); a second model family on pass 2 compared on the same runs.
- D16 Example spec values come from Lean's compiled evaluator (`FVA.Explain.run`, `evalExpr`), so an `implemented_by` override shows a value the kernel never sees (cheat 5's `sumBelow`). → each displayed spec value confirmed by kernel defeq (`decide (res = v)`), mismatch shown as such; cheat `sumBelow` example shows the kernel value.
- D17 Too-costly example cases cost `CASE_TIMEOUT` (10 s) each, crash path ~25 s (interpreter deep-recursion abort dumps 1.3 M frames). → per-case budget enforced inside Lean (heartbeats or kernel `maxHeartbeat`) instead of process kill; `sum_to(4294967295)` reports `too costly` in ≤ 2 s.
- D18 Examples cover only `∀ BitVec…, Returns` claims; relational claims (`≤`, `∃`, implications) show the elaborated statement alone. → for a `Prop` body decidable at concrete inputs, show input → true/false rows; a claim `∀ n, Returns m "f" [n] [r] → r ≤ n`-shaped example in a test project renders rows.
- D19 `fva trust` replay fails inside agent sandboxes (nested `bwrap`: `Failed to create NETLINK_ROUTE socket`), pushing agents to `--inadvisably-no-sandbox`. → replay detects a nested-sandbox launch failure, reports it as `replay: not run (sandbox)` distinct from a kernel rejection, and offers a supported fallback; `fva trust examples/toy` under `codex exec -s workspace-write` reports that state instead of FAIL.
- D20 Benchmark v1 (`prototype/bench/results.md`) too small to separate arms on correctness. → v2: ≥5 tasks needing memory, calls, `br_table` (after D1), README without the wasm hint, n ≥ 3 per cell, readability by proxy metrics only (lines + definitions to trust, LLM-judged); result table states per-metric gap with spread.
- D21 FVA's cheat suite tests FVA's own audit, never the checker; pinned verifiers ship soundness bugs. → `fva trust` runs a committed canary set of known-false proofs per pinned Lean toolchain (each must be rejected by every kernel it uses) + reports the kernel set; a canary that passes = trust FAIL with `[checker]`.
- D22 Only program verification is offered; components that resist it (compilers, interpreters, code generators, LLM pipelines) need per-output certification. → `fva certify` link path: a Lean checker spec over (input, output) pairs + kernel-checked acceptance per committed output; demo = a toy compiler's committed outputs certified, one tampered output rejected.
- D23 Spec size unbounded: agents grow specs toward implementation size with no gate. → `fva trust --surface-budget N` (and a project config value) reports `[surface]` FAIL above the budget + names the largest review modules; `examples/toy` passes at 20, fails at 5.
- D24 Plain-English review rests on LLM informalization; a controlled language gives a deterministic one but loses meaning where its grammar cannot carry a statement. → evaluation unit: claims for toy + bench tasks written in a small FVA controlled language that elaborates to the same `Prop`s (`Iff` proven by `rfl`), measured coverage of the bench requirements, compared against `fva explain` on the same claims.
- D25 Review state is not part of the verdict: a PASS reads as "verified" with no human approval. → port tag `archive/review-ledger` + `archive/attest`: `fva trust` reports FAIL / PROVEN, UNREVIEWED / VERIFIED from approvals keyed to elaborated-statement + wasm hashes; `fva attest` signs them (in-toto Statement v1, `ssh-keygen -Y sign`) and verifies against verifier-chosen signers; a project-supplied signer list never attests; the tag's QA matrix (sign before review rc 2, tampered statement / foreign key / edited spec → NOT VALID) reproduces.
- D26 Every claim costs bespoke review. → port tag `archive/pattern-catalog`: claims that are literal instances of reviewed-once catalog patterns show one fixed sentence each; matching by elaborated expression, never LLM; a project-local module named like a catalog module stays reviewed; toy-catalog trust PASS + cheat 7/7 bespoke.
- D27 Review happens in a terminal wall of text. → port tag `archive/review-page`: static HTML review desk from `fva trust --json` + saved explanation, per-claim Accept/Reject + note, receipt bound to the snapshot, `--status` rc 0 only for full acceptance + current explanation + trust PASS; screenshots inspected at desktop + mobile width.
- D28 WASI file I/O is unmodeled (user ruling: deferred this phase; the bench subjects are pure core wasm or call host functions under stated contracts), so whole CLI programs (bustools count, bcftools norm) get per-output certificates only. → reviewed-once WASI preview1 model (files, fds, preopens, args/env); the bustools count-only wasm build (`fromtext` + `count` on upstream test tc0004) lifts and a claim about the bytes it writes to `output.mtx` is proven.
- D29 Wasm exception handling is unmodeled (user ruling: deferred), so C++ built with `-fwasm-exceptions` is rejected as unsupported. → `try_table`/`throw`/`throw_ref`/exnref in syntax, decoder, semantics + type-soundness proof; the official exception-handling spec tests pass; a C++ function that throws and catches lifts and its claim is proven.
- D30 `memory_copy.wast` through the reference stepper exceeds 900 s (memory as a closure chain over writes + per-byte expansion of `memory.copy`), so `scripts/test-spec` full mode leaves it out. → the optimized machine (U4 contract I1: value stack + zipper + chunked memory, proven against the stepper or `Step`) runs it. Acceptance: `scripts/test-spec memory_copy` reports the pinned 4386/0/64 in < 300 s and the full mode includes it again.
