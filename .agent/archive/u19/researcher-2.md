This limits the claim: splitting source scripts alone is not sufficient when their types still force giant definitional comparisons.

## B5 — suggested correspondence contract (synthesis, not implemented)

- Let `Rep modelState machineConfig` expose only the locals, stack/control position, relevant bytes, and framed remainder required at a loop cutpoint.
- For each branch, prove an actual finite machine segment via `walk`/context rules reaches the next cutpoint and updates `Rep` according to one model step. Attach a decreasing `Nat` measure (or lexicographic measure for nested phases); prove the terminal segment as well. The existing FVA source supplies the transport lemma: `/home/eturkes/Projects/fva/FVA/Proof/Lib/Walk.lean:46–60`, “`(h : walk k c = some c') (hc : Must H Q c') : Must H Q c`”.
- Close the correspondence by well-founded induction. Model proof then reasons about the algorithm without instruction lists. The model remains proof-side scaffolding; the claim continues to mention the original byte-checked module, not a rewritten source or separately trusted implementation.
- Fuel alternative: choose a structurally recursive evaluator returning timeout/error/success; prove the simulation for adequate fuel and a sufficient-fuel bound for every input in the contract. Merely assuming some successful run or proving a bounded testcase is weaker than FVA's total all-input claim. Source anchor: `/home/eturkes/Projects/fva/FVA/Proof/Exec/Det.lean:467–469` requires “`runDet n c = some c'`” before obtaining `Must`.
- **Footprint is separate:** `Changed` only says “`∀ a, P a → after.byte a = before.byte a`” at `/home/eturkes/Projects/fva/FVATest/Subjects/EdgerCpm/BodyFrame.lean:12`. Logical counterexample: a load outside the buffers does not change those bytes, so a final-state equality can hold while the no-read condition fails; a write followed by restoration also defeats a final-only write-frame statement. Inference: each route needs a step/trace-local access property, including called helpers, rather than adding only a final-state conjunct to the result relation. If the present `Step` relation omits access events, derive the footprint structurally from the executed instruction and effective-address premises, or add an independently justified trace relation; this research did not inspect/implement that relation.
- Direct-invariant and model-refinement routes share machine-segment obligations; there is no sourced guarantee that refinement wins for this decoder. Compare them on the same loop with the same termination + functional + access contract and independent replay. That is an experiment recommendation, not a quantitative prediction.

## B6 — current toolkit and residual limits

- [4.35 `Sym/Simp/SimpM.lean`](https://github.com/leanprover/lean4/blob/v4.35.0/src/Lean/Meta/Sym/Simp/SimpM.lean) explicitly targets “large terms typical in symbolic execution”. Its design goals are “Efficient caching via pointer-based keys on maximally shared terms”, “Fast pattern matching ... instead of `isDefEq`”, “Minimal proof term overhead”. It documents standard-simp problems: structural cache collisions “O(n²)”; `inferType` during proof construction “destroys sharing”; contextual `ite` cache invalidation “O(2^n)”. These are source design claims, not measured FVA asymptotics.
- [4.35 `Sym/Simp/EvalGround.lean`](https://github.com/leanprover/lean4/blob/v4.35.0/src/Lean/Meta/Sym/Simp/EvalGround.lean): predicate lemmas “short-circuit the standard `decide` proof chain”; “avoids reconstructing `Decidable` instances at each call site”; maximal sharing makes equal subterms pointer-equal. It also states its dispatch “assumes non-standard instances are not used.” Inference: `Sym.simp`/`sym =>` is a relevant candidate only if profiling identifies ordinary simp/term sharing as the bottleneck; it is not a drop-in claim that FVA's tactics will improve. Not ported or benchmarked here.
- [4.35 release](https://lean-lang.org/doc/reference/latest/releases/v4.35.0/), #14802: `let_to_have` “unblocks the efficient `have`-telescope machinery of `Sym.simp` (`simpLet`), which does not process dependent `let`s”; #14768 `lift_lets` merges declarations with equal definitions. These address elaboration/representation costs, not the separate kernel defeq traps in B2/#14803.
- [#14803](https://github.com/leanprover/lean4/issues/14803) is open in fetched page text and reports application-vs-lambda eta comparisons of a function-valued interpreter. It is relevant to function-valued memory/model expressions, but applicability to FVA's exact proof and final 4.35 remains unconfirmed. Do not report the nightly failure as a reproduced final-release defect.
- Heartbeat control is a budget, not a proof optimization: [4.35 CoreM](https://github.com/leanprover/lean4/blob/v4.35.0/src/Lean/CoreM.lean#L30-L33) defines `maxHeartbeats` as allocation-thousands and `0` as unlimited. The LNSym kernel regression already persisted with `maxHeartbeats 0`; source #14331 says “kernel TC enabled (`maxHeartbeats 0`) ... ~30 min”.
- `.olean` search yielded [Zulip's olean-dump thread](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/olean.20dump.20tool.html), which discusses sharing and historical proof-body storage; it does not establish a modern cap. [Lantana performance](https://github.com/mit-pdos/lantana/blob/main/docs/performance.md) is primary but not a compiled-machine-code benchmark: its [README](https://github.com/mit-pdos/lantana) calls it “a concurrent separation logic for liveness ... on top of Transfinite Iris-Lean”. Its performance document says machines/parallelism differ and “the two numbers are not a benchmark.” No `.olean` size threshold from that source is used.
